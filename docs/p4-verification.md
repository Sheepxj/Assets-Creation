## 3. 实际 HTTP

compose.p4.yaml + scripts/smoke-p4.mjs，使用独立 3001 端口、真实 Cookie／CSRF、MySQL 和文件卷。full 模式 **7 项通过**：

1. 登录／CSRF／服务端参数与素材校验。
2. 连续两次提交各在 1500 ms 内返回 202；两任务仍未结束、第二条 QUEUED。
3. 同键同内容原 ID，同键不同内容 409；未成功结果不可读。
4. 实际观察 MATERIAL_CHECK、GENERATE、FINALIZE；第二条 startedAt 不早于第一条 finishedAt。
5. 两个独立结果 URL，图片哈希匹配仓库预置图；多次查询成功 DTO 不变。
6. B 无法伪造 A 的详情／结果／历史，分页及 active 正确。
7. 创建第三个任务后停止全部查询，等待超过配置总耗时，以新客户端登录后直接读到 SUCCEEDED。

成功组耗时配置 500／1500／500 ms。之后等待旧任务结束，分别重建 Java、将 SIM_FAIL_STAGE 设置 MATERIAL_CHECK、GENERATE、FINALIZE，failure 模式各 **1 项通过**；核对失败阶段、原因、前后步骤及结果 404，而非仅看 HTTP 请求返回错误。

## 4. 强制中断与正常停止

**强制中断**：配置 15000／0／0 ms、MATERIAL_CHECK，prepare-restart 创建一条执行中及一条排队任务；立即 SIGKILL Java。新容器改为 0／0／0 ms、NONE，verify-restart **3 项通过**：

- 旧会话 401；执行中任务 FAILED／SERVICE_RESTARTED，保留 MATERIAL_CHECK，当前步 FAILED、后两步 PENDING。
- 原排队任务继续使用旧快照，最终在素材检查发生指定模拟失败，而不是按新 NONE 配置成功。
- 先前成功及三种模拟失败的记录保持原 DTO。

**正常停止**：配置 6000／0／0 ms、NONE，prepare-graceful 创建两任务，立即 `stop -t 25 backend`。Java 停止后从 MySQL 直接读取快照中的两个 UUID，确认当前 **SUCCEEDED**、另一条 **QUEUED**；不是等重启后倒推停止行为。重建后 verify-graceful 通过，排队任务成功，先前终态仍相同。额外读取五份成功结果（原三份及正常停止两份），逐份 PNG 哈希与仓库一致。

准备 ID 本身有独立检查；不把准备次数重复算成新的业务测试。完整复现和参数恢复见[任务说明](tasks.md)。专用任务、素材、卷保留；快照含 Cookie，只在被忽略的 .local 中保存，不提交 Git、不打进镜像。默认开发项目未参与 HTTP 写入。

## 5. 发现与修正

- 历史接口非法枚举经通用异常处理返回 500：增加 MethodArgumentTypeMismatchException→400／INVALID_PARAMETER，非法数字同样处理，完整回归通过。
- 一轮自动化与实际 worker 误连同一测试库，导致测试夹具被后台领取、HTTP 任务被另一测试执行器改变。该轮失败不计为通过；改成两个独立 Compose／数据库项目后，91 项及全部 HTTP 场景重新验证通过。未以禁用实际 HTTP worker 回避问题，也未修改默认开发数据。
- 加强最后步骤／任务成功原子提交的故障点，将故障移到最后步骤已写入后的任务条件更新，验证真实回滚；加强重建后的结果文件哈希读取。

## 6. 当前边界及下一阶段

- 默认 3000 环境已升级 P4；三服务正常，模板及身份接口沿用，任务接口已可调用。首页仍是工程入口，P5 才开始正式模板／登录／上传／提交页面，P6 补多任务／历史及轮询。
- 只支持单 Java 后端，不能同时启动多个实例消费同一个库；当前互斥与恢复不是分布式调度协议。
- MySQL 与文件系统不是分布式事务；崩溃、提交结果不确定或清理 I/O 失败可能留下未关联结果，失败／未完成任务不开放结果；缺文件返回 404，无自动清理。
- 关闭窗口外的执行留待启动恢复，不保证继续执行；重启后会话需重新登录。不提供失败任务重试、取消或自动续跑。
- 持续数据库故障会阻止状态保存和继续领取，不用内存伪造成功；恢复后重试保存或启动恢复明确失败。
