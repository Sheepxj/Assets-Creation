## 2. 修复的三个边界

### 终态发现路径统一同步

P5 仅在详情查询得到终态时失效历史缓存。若该详情因请求错误暂停，而 recent 查询先发现终态，原代码只更新 registry，当前筛选历史可能仍为空。

TasksProvider 现在在终态发布后统一同步：每个身份下的新终态只处理一次，写入对应详情缓存，并失效 history 前缀及 recent。详情、近期记录和分页历史的发现路径均覆盖，后续 PENDING 不假装执行。

### 迟到非终态不倒退阶段

P5 已保护成功／失败终态，但旧 active 或历史响应仍可将已观察的 GENERATE 改回 QUEUED／MATERIAL_CHECK。TaskRegistry 现在还检查非终态的阶段顺序，拒绝倒退，允许正常向后推进；没有根据浏览器时间推算进度。

### 筛选结果缩小后的可达页码

任务完成后，RUNNING 等筛选的总数可能从 13 降为 12。原第 2 页会变为空且缺少分页出口。History 现在根据新 total，在提交当前组件渲染前将超界页码调整到最后可用页，按新 queryKey 获取有效页面，保留筛选。

## 4. 真实浏览器验证

使用 `assets-creation-p6` 独立 MySQL／文件卷和三服务，地址 `127.0.0.1:3001`；与默认 `localhost:3000` 隔离 Cookie 主机。通过容器内真实 Java API 为专用 demo_a 准备 25 条成功和 1 条 GENERATE 指定失败任务，均等待实际终态；浏览器再提交两条，最终共 **28 条（27 成功、1 失败）**。默认用户数据未参与写入。

浏览器实际操作：

1. 登录 A，分别浏览第 1／2／3 页，最后一页禁用下一页；失败筛选回第一页、仅一条，QUEUED 初始为空；原因和后续未执行正确。
2. 上传 PNG、JPEG 连续提交两条真实任务。使用 10000／20000／10000 毫秒专用快照观察排队与当前阶段；导航历史后刷新，仍有两条未完成任务及独立卡片。
3. 仅 stop 专用 frontend，保留 Java 与 MySQL 运行。页面出现网络查询异常，原 GENERATE／QUEUED 数据保留，不变成 FAILED。start frontend 后手动“刷新记录”，异常消失，读取第一条成功及另一条未完成，徽标 2→1；随后第二条成功，徽标归零，RUNNING 筛选自动变空。
4. 375px 窄屏筛选失败／成功、查看记录；成功图片预览真正加载，焦点进入关闭按钮，Escape 关闭且回到原预览按钮。
5. 窄屏进入三图模板，三个上传位、主按钮无横向溢出；Tab 正确进入第二个带标签上传位且焦点可见。
6. A 已登录时直接在登录页切 B，B 无任务且没有 A 的用户名或卡片；再登录 A，28 条持久记录仍可读取。
